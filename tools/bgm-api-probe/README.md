# Bangumi 高级搜索 API 实测结论

`POST /v0/search/subjects` 的官方 schema 自称「实验性 API，本 schema 和实际的 API 行为都可能随时发生改动」。
**实测确实如此**：文档承诺的能力未必落地，文档没写的限制却真实存在。季度片单（`feature/search` 的
`SeasonalGuideViewModel`）的取数策略建立在这些结论上，所以它们必须可复跑、可证伪。

```bash
python tools/bgm-api-probe/probe_search_api.py
# 退出码 0 = 既有结论仍成立；1 = 有结论已失效，取数策略需要复核
```

实测日期：2026-09-29（2026 夏，`air_date ∈ [2026-06-21, 2026-09-20]`，季总量 249）。

## 1. `limit` 有 20 的硬上限，且静默截断

官方 schema 只把 `limit` 声明为普通 `integer`，**没有任何 `maximum`**。实测：

| 请求 limit | 20 | 25 | 30 | 50 | 100 |
|---|---|---|---|---|---|
| 实际返回 | 20 | 20 | 20 | 20 | 20 |

不报错、不降级，直接按 20 截断。因此 `PAGE_SIZE` 必须锁死 20，翻页进度才能与响应 `total` 对上。

> 曾据此评估过「一次拉全季」方案：一季 249 条 = 13 个请求，代价过高，已放弃。

## 2. 深 `offset` 在季量级完全可用

季量级（total 249）下 `offset=0/100/200` 均正常返回满页，`offset=300`（超出总量）返回空。
`total` 有 **1000 的硬顶**（符合 meilisearch `maxTotalHits` 默认值，`offset >= 1000` 即空）——
对季度片单无影响（249 ≪ 1000），但跨季大范围浏览会撞上。

## 3. `meta_tags` 的 `-` 排除语法：文档承诺，**实际未实现**

官方文档原文：

> 公共标签。多个值之间为 `且` 关系。**可以用 `-` 排除标签**。比如 `-科幻` 可以排除科幻标签。

实测全部落空——`-` 被当作**字面标签名**，匹配不到任何条目，直接返回 0：

| 表达式 | 返回 total | 若排除生效应为 |
|---|---|---|
| `["剧场版"]` | 34 | — |
| `["-剧场版"]` | **0** | 215 |
| `["-短片"]` | **0** | 230 |
| `["!剧场版"]` / `["NOT剧场版"]` | **0** | 215 |
| `["TV","-剧场版"]`（正+负） | **0** | ≤84 |
| `tag: ["-剧场版"]`（换字段） | **0** | — |

**这条直接否掉了「用排除法把『正片』下推服务端」的方案。** 别再照文档重试一遍。

## 4. `meta_tags` / `tag` 多值 = AND；无「或」、无排除

`["剧场版","短片"]` 与 `["剧场版","MV"]` 均返回 0（无交集），确认 AND。
`tag` 与 `meta_tags` 是**两套不同的命名空间**，同名标签计数不同（剧场版 38 vs 34，TV 101 vs 84）——
代码用 `meta_tags` 是对的，它是「公共标签」那套分类。

## 这些结论对取数策略的约束

服务端能做的一共只有：`type` 支持**或**（但取值是书/动画/音乐/游戏，对形式筛选无用），
其余 `meta_tags` / `tag` / `air_date` / `rating` / `rank` **全是且、且无排除语法**。

所以「正片 = TV 或 WEB 或 OVA」「欧美 = 6 个标签取或」这两类**在服务端无解**，只能客户端补筛。
fan-out（每个标签发一次再合并）更不划算：欧美要发 6 次、每次还得各自翻到底，
请求数远多于把整季拉一遍。

既然只能客户端筛，就必须避免「筛选一变就重新取数」——那等于拿**完全相同的请求**重取一遍，
还把已加载的页与滚动位置全丢掉。这正是 `SeasonalGuideViewModel` 里
`RequestKey` + `distinctUntilChanged` 存在的原因：**换挡判据是「请求是否真的变了」，
而不是「筛选条件是否变了」**。改动前请先读 `SeasonalGuideViewModelTest` 里
`clientOnlyFormFilter_doesNotRefetch_andLoadMoreWalksUntilSomethingIsVisible` 与
`selectWesternOrigin_doesNotRefetchBecauseTheRequestIsUnchanged` 两条钉子。
